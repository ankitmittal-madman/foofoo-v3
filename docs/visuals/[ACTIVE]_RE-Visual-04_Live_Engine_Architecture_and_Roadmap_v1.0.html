Ghar RE — Live Engine Architecture & Roadmap

The actually-deployed recommendation engine (ghar_re_core / ghar_re_service, Python, Fly.io) — distinct from the earlier RE-Visual-01/02/03, which describe a legacy TypeScript engine confirmed as dead code and deleted this session. Companion document: [DRAFT]_WP-14_RE_Intelligence_Roadmap_v1.0.md.

Why this doesn't jump straight to ML: public.feedback_events has 0 rows, live-verified. There is no interaction signal to learn from yet — only "a plate was served," never "a user liked or rejected it." The roadmap below sequences a class-based module registry and real feedback capture before any learned ranking, matching how Zomato/Swiggy/Netflix's own recommendation systems actually evolved historically.
1 · Derive household profile (θ)live
ghar_re_core/derivation.py::derive_theta() — raw Q1–Q15 onboarding answers → region, blend, income band, spice ceiling, is_jain, weaning_present, rho_disc (discovery dial), veg_days, meat exclusions.
↓
2 · Hard filters (A1–A5)live
scoring.py::eligible() — diet, jain, allergen (basic pass only — hidden-derivative layer not yet wired, see Known Gaps), weaning floor, fasting mode. Pass/fail only, no scoring. Reduces the 810-dish catalogue to the eligible pool for this household+context.
↓
3 · BASE scoring — Σ W_k · conf_k · m_k(x)live
Every eligible dish scored by summing 8 weighted terms: m_palette, m_slot, m_season, sig, m_age, m_household, m_weather, prior_boost. Currently hand-written functions called directly in base() — not yet the pluggable ScoringModule registry RE-DOC-11 §7 specifies. See "Class-based registry" tab.
↓
4 · GAIN_Q15 objective multiplierlive
The household's stated objective (awesome_taste / healthy_living / into_fitness / protein_calculator) reweights the BASE score.
↓
5 · Pairing guardrails + compat()live
pairing.py::allowed()/compat() — hard gates (no two rich gravies, no two same-base dishes, cuisine coherence) plus a soft richness/protein-balance nudge. Known data-scope gap: the protein-balance term only checks one of its four named categories (flagged in code, not fixed — a scoring-output-changing decision for the Founder).
↓
6 · Assemble-7 (greedy MMR-style)live
pairing.py::assemble_7() — best-score-first, no-duplicate-hero guard, discovery-dial cap for experimental/exploratory plates (driven by rho_disc). Deterministic: same household + same context always produces the same 7 plates (see WP-8G, "Refresh" variety gap).
↓
7 · Decision trace (funnel + near-misses)DB live, RE not yet deployed
Added this session (WP-12): per-request funnel counts through each filter stage, served plates, and top-5 near-miss alternatives with a concrete reason each lost. recommendation_events.decision_trace column is live; the updated ghar_re_service has not been redeployed to Fly.io yet, so it's still NULL on real requests.

RE-DOC-11 §7 already specifies this — it is not implemented yet. Today's 8 BASE terms are plain functions; this is what turns them into the registry ML plugs into later (§8) with zero changes to the composition loop.

Data foundationno ML

1
Class-based module registryno ML
Implement the ScoringModule protocol (RE-DOC-11 §7). Migrate all 8 BASE terms into registered modules with config-driven weights. Must be score-neutral — a refactor, not a rescoring — proven by the existing golden-master tests.
Done when: base() is a registry loop, not hand-written summation, and every existing test still passes unchanged.
2
Variety / explorationno ML
WP-8G's exclude_dish_ids contract extension, plus a lightweight non-learned exploration mechanism (epsilon-greedy or a simple class-level bandit). Needs only served/rejected counts, not labels. The single biggest "feels intelligent" lever available before any ML — refresh stops being deterministic.
Done when: two consecutive Refresh calls can legitimately differ, explainable via decision_trace.
3
First learned module — s_prefML, gated on Phase 0 volume
Once feedback_events has real density, add a learned preference module (start simple — logistic regression or a small GBDT over structured features + existing module scores; label = accepted/rejected). Plugs into the Phase 1 registry with zero composition-loop changes, per RE-DOC-11 §8.
Done when: a real held-out evaluation shows improved acceptance over the rule-only baseline, and it's disable-by-config.
4
Collaborative signalML, gated on density
Two-tower retrieval or ALS-style CF, gated on interaction density crossing a real threshold — out of scope to design in detail before Phase 3 even ships.
West-MH rain comfort hero missing from the real catalogue
"Kanda Bhaji" (KB §R3 West-MH rain comfort hero) does not exist under that name — or any close spelling — in the real 810-dish catalogue. Confirmed by direct search this session. A second entry ("Pithla-Bhakri" vs. the real "Pithla Bhakri") has a hyphen/space mismatch with the same silent-no-op effect. Flagged at the data source (ghar_re_core/knowledge.py), not fixed — picking a replacement dish is a domain call.
household_context unwired
Table exists, RLS applied, one read function exists — but nothing calls it and nothing writes to it. Every request uses caller-supplied context or a hardcoded default, never real recent history.
Allergen hidden-derivative table inert (pre-launch blocker)
The Core Spine's own §D states allergen filtering is "not safe-complete" until this lands. ghar_re.allergen_hidden_derivatives exists but is_active=false.
Fallback plate is one hardcoded dish, not per-zone
Every RE failure serves the same pan-India Moong Dal Khichdi regardless of the caller's region, diverging from RE-DOC-10 §11's "cached-per-zone default plate set" spec.
