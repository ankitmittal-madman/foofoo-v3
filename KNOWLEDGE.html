Recommendation engine
The class-first RE: a household resolves to a cohort, the cohort to a weekly class plan, each class to a dish pool, and the engine picks the slate. One reusable engine owns every recommendation decision; recommendation logic exists only in supabase/functions/_shared/services/re/. Authority: DOC-P3-03 §06–11, RE-DOC-01–05, WP-8D/WP-8E.

Cold start → warm start
Day-0 confidence is computed from onboarding answers (LF-A08), clamped to the documented 0.40–0.65 Day-0 range (DCR-8E-01 cap at 0.65); cold_start_mode holds while interaction_count is low. Cold-start ranking leans on CohortPrior (w≈0.55 at tier 1) + exploration (Thompson sampling, Beta(1,1)=uniform at start, bounded bonus). As interactions accumulate, the weight ladder (5 tiers, continuous forward-transition interpolation — DCR-8D-01) shifts weight from cohort priors toward PersonalHistory/ContentMatch. Current limitation: re_cohort_class_priors is unseeded, so cold-start CohortPrior = neutral 0.50 fallback (LF-E02) until seeded.
One engine, three callers (DCR-P3-06-007; proven in the WP-8E integration test)
OnboardingOnboardingOrchestrator runs LF-A01–A09 (its own logic), then invokes engine.generateWeekPlan, persists via WeekPlanStore, returns the §06.2 handle. Per the CDM Domain Events, the RE Engine is the first-plan actor (AD-01 reconciliation, WP-8D §1).
RecommendationsRecommendationService (POST /v1/recommendations, §06.4) invokes engine.generateSlate for one slot, persists the fresh slate + FinalScores.
Nightly schedulerNightlyPlanScheduler (LF-L01, 23:30 UTC / 05:00 IST when deployed) iterates eligible users through the same engine; single-user failures isolated.
History, context & evolution
History: the engine reads the append-only event stream (never writes user tables — RE-DOC-01 isolation); PersonalHistory decays with λ=0.05; Not-Today suppression decays with threshold + context override; Never list is a hard constraint. Context: ContextFit multiplies weather/season/day against genome tags (re_context_multipliers, seeded); weather via 12h weather_cache. Evolution roadmap (RE-DOC-05, behind the stable /v1 contract via re_engine_versions): classfirst_v1 (active) → classfirst_v2 → ltr_v1 → ml_v1; /v2/recommendations reserved, unimplemented. No pgvector/LLM infra exists today by design (DOC-P4-00 §28).

S39 · Jul 29
If the engine is on the public internet, what actually protects it?
The signed-request check, and only that. Every call must carry a signature computed from the exact request bytes and a secret held only in Fly's and Supabase's encrypted stores; unsigned, altered, wrong-secret and replayed requests are refused before the request is even read. The important consequence is stated plainly rather than softened: there is no longer a network layer behind it to catch a mistake in that code, so it is the one thing that must never be weakened.
S39 · Jul 29
Why build a rate limiter in our own code instead of using the hosting platform's?
Fly's proxy has no per-source rate limiting — its only related setting caps how many requests run at the same time, which a determined caller sidesteps by sending them one after another instead. Both are now in place: the platform setting as a memory backstop, and our own limiter as the actual rate cap.
S39 · Jul 29
Why does the limiter run before the signature check rather than after?
Because the whole purpose is to protect the signature check. Placed after it, every flooded request would already have cost the engine its cryptographic work, and the limiter would be decorative. It relies on a subtle framework ordering rule, so a test pins it: an unsigned request that is over the limit must be answered "too many requests", not "unauthorised" — the latter would prove the expensive step ran first.
S39 · Jul 29
Why is the limit set so high, and why are health checks exempt?
Our app's calls arrive from a small pool of shared addresses, so many genuine users look like one caller — a tight cap would throttle customers rather than attackers. It is adjustable without rebuilding. Health checks are exempt because refusing the platform's "are you alive?" probe would get the machine declared dead and restarted, making the protection cause the exact outage it exists to prevent.
S39 · Jul 29
Why does the limiter let traffic through when it fails, while the security check blocks it?
They protect against different things. A missing safety damper should never become a self-inflicted outage, so if the limiter hasn't loaded, requests pass to the security check. A missing secret is the opposite: the engine refuses to start rather than serve anything unverified. The asymmetry is deliberate, not an oversight.

Key line of code
if (!timingSafeEqual(token, ctx.config.supabaseServiceRoleKey)) throw ... ← rejects anything except the exact project credential, compared in a way that can't leak timing information
Why not just re-enable the standard login check instead of building something new?
The standard login check only verifies a regular user's token — it has no way to verify the special service credential these jobs are meant to use, and would actually reject it. A dedicated check was the only way to actually restrict this to the scheduler.
