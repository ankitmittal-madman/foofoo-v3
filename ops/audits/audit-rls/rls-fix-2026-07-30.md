# RLS Audit — Resolution — 2026-07-30

Addendum to `rls-audit.md`. Original findings not modified, per this repo's versioning rule
(never edit a prior record in place — append the outcome).

## Finding 1 — partition-child tables (interaction_events_2026_07/08/09, suggestion_logs_2026_07/08/09)

**Outcome: no fix applied — investigated and confirmed a false positive.**

Empirically verified live: `interaction_events_2026_07/08/09` and `suggestion_logs_2026_07/08/09`
are true declarative partitions (`pg_inherits` confirmed). Ran `EXPLAIN` under
`SET ROLE authenticated` with a synthetic JWT claim directly against a partition child by name —
the query plan showed the exact same RLS filter (`profile_id = auth.uid()`, real Bitmap Index Scan
on `profile_id`) as the parent's own `ie_select_own`/`sl_select_own` policies. Postgres
automatically applies a partitioned table's RLS policies to every partition regardless of access
path. The original audit's "silent default-deny dead end" framing was incorrect — there is no
security gap and no PostgREST bypass here.

## Finding 2 — 7 internal tables (audit_log, derivation_conflicts, coverage_gap_log,
safety_gate_log, push_notification_logs, feature_flags, etl_job_runs)

**Outcome: real gap found, but not the one the original audit named — fixed via migration 039.**

`019_rls_policies.sql` documents these tables as intentionally RLS-disabled, on the assumption
they have no PostgREST-reachable grants. That assumption is false live: `anon` and `authenticated`
both held full `SELECT/INSERT/UPDATE/DELETE/TRUNCATE` grants on all 7 tables (Supabase's default
public-schema grant, never revoked by any canonical migration for these specific tables).

**A first attempt to "fix" this by disabling RLS to match 019's literal text was wrong and was
reverted within the same session** — with those grants in place, disabling RLS would have made
all 7 tables fully readable/writable by any client via the REST API. This was caught immediately
via Supabase's own security advisor, which flagged `rls_disabled_in_public` (ERROR level) the
moment RLS was disabled.

Further investigation found `029_pf1_security_hardening.sql`'s own header documents a **Founder
decision (2026-07-13, "Option B")**: a production-only operational overlay
(`public.rls_auto_enable()` + an `ensure_rls` event trigger, deliberately kept out of canonical
migrations for clean-rebuild determinism) automatically re-enables RLS whenever it's found
disabled — explicitly because 019's "protected by lack of grants" assumption was never true. What
`audit-rls`'s original report called "drift from 019's documented intent" is that approved
overlay doing its job, not a bug.

**Actual fix applied (migration `039_rls_internal_table_drift_fix.sql`):** RLS left ENABLED on all
7 tables (matching the live, Founder-approved state — no ALTER ... DISABLE anywhere in this
migration). As defense-in-depth, matching the exact precedent already set in
`029_pf1_security_hardening.sql` Finding 2 (column-level REVOKE on `dishes`), this migration
revokes the unnecessary broad grants for `anon`/`authenticated` on all 7 tables. Verified live
post-fix: zero `anon`/`authenticated` grants remain on any of the 7 tables, and Supabase's security
advisor reports zero ERROR-level findings for any of them (only the expected INFO-level
"RLS enabled, no policy" note, which is correct for internal tables with no client-facing policy).

## Finding 3 — seed rollback scripts (rollback-readiness audit, not audit-rls)

`database/rollback/101_seed_reference_data_framework_rollback.sql` and
`database/rollback/102_seed_illustrative_content_and_dependents_rollback.sql` were written and
dry-tested live (inside a transaction, rolled back, not committed). Discovered: later seeds
110-121 build genuine dependent content on top of 101/102's "illustrative" rows using
`ON CONFLICT DO NOTHING` on the same natural keys (e.g. `117_seed_re_dish_linked_icd1.sql` adds
`re_class_dish_options` rows FK'd to meal classes 101 created) — so, like every rollback in this
repo, 101/102's rollback must be applied only after every later seed's own rollback has already
run, in strict reverse numeric order. Both files document this explicitly in their own headers.
