01 · Executive summary

The answer to “Aaj khaane mein kya banaye?”

Ghar RE is an Indian household meal-decision product. It converts household composition, food rules, regional familiarity, goals, context and feedback into a weekly class plan and daily dish choices—without pretending to be a medical service, food-delivery marketplace, calorie diary or social network.

Problem

Daily meal choice is repetitive, negotiated and constrained. Generic recipe search creates more options; Ghar RE aims to make a safe, familiar, useful decision.

Primary user

The person planning for a household—represented by the Meera persona: 32, Pune, Bhopal roots, partner and children, balancing familiarity, health and time.

Core difference

Household-first, Indian-context, class-first planning. It chooses a meal pattern before choosing a dish and uses hard safety gates before soft relevance.

810

131

meal classes that create a stable planning vocabulary

0

active trained preference models; present personalization is bounded and rules-based

Product in one flow

Household truth→Hard safety filters→Meal-class plan→Dish ranking→Plan & cook→Feedback memory
Reality today: a working rules-based planner with immediate dish-level affinity, persistence and suppression. Long-term direction: a governed household food-intelligence system with richer nutrition, pantry, seasonal, price, festival and learned-ranking signals.
02 · Product vision

Reduce decision fatigue, not human agency

Mission

Make everyday Indian meal planning feel obvious: suitable for the whole household, grounded in familiar food patterns, adaptable to the day, and easy to change.

Product promise

“Give me a plan I can trust, enough alternatives to stay in control, and recommendations that improve when I respond.”

Goals

  • Fast, safe meal decisions
  • Household-wide usefulness
  • Familiarity plus bounded discovery
  • Visible reasons and control

Non-goals

  • Medical diagnosis or treatment
  • Delivery marketplace
  • Precise calorie tracking
  • Unbounded AI recipe invention

Users

  • Family meal planner
  • Solo urban professional
  • Fitness-oriented solo user
  • Future: multi-member collaboration

Trust boundary: the client does not directly own recommendation logic. Supabase validates identity/ownership and holds mutable user state; it calls the Fly service with HMAC. The engine ranks an immutable bundle and does not directly query the database.

Four conceptual layers

  1. Meal genome: dish attributes
  2. Food graph: bounded relations
  3. Household intelligence: derived profile
  4. Contextual meal science: slot, weather, objective

Runtime split

Mutable: users, plans, events, feedback, suppressions.

Immutable per release: catalogue, rules, weights, graph bundle.

Why this shape works

Deterministic, inspectable ranking; narrow database access; reproducible releases; future model seam without forcing ML into the current product.

08 · Recommendation engine deep dive

Safety first, class first, dish second

flowchart TD
      Q[Request: household + slot + context + surface] --> N[Normalize answers and derive theta]

      D --> E
      L --> E

1. Inputs and derived household state

Raw household answers are normalized into a deterministic profile (“theta”): geographic palette, lifecycle, household type, dietary constraints, time pressure, objective and related routing signals. This derived state is computed live; a stored persona ID is not the ranking identity.

2. Hard filters—never traded for relevance

vegetarian / non-veg rulesmeat restrictionsJain compatibilityallergensweaning rulesfasting rulesNever listNot Today suppressionoptional calorie lens

3. Scoring equation

score = BASE(dish, household, context) × GAIN(objective) + w_cohort(n) × S_cohort − w_foreign(n) × S_foreign + w_pref × S_pref
Today S_pref = 0. Daily planning then applies bounded online affinity (implemented as a controlled score multiplier) and selection/diversity logic.

BASE

Configured modules cover palette and distance, meal signature, time, household fit, weather/comfort, priors and other frozen-spec signals. Parameters load from YAML; missing values raise instead of being invented.

GAIN

The selected objective—such as taste or healthy living—changes the balance of indulgence, lightness and protein, then clamps the multiplier.

Cohort

A compositional class plan blended with a learned offline frequency model gives graded class affinity. Its weight starts strong and decays with interactions.

Exploration

Epsilon-greedy selection can swap an under-served meal class; default configured epsilon is 0.15, with a code-level safe default of zero if config is absent.

Pairing

The general pipeline may combine dry/liquid dishes using cuisine distance, same-base exclusion, taste balance, protein and duplicate/discovery constraints.

Explainability

Score contributions and exclusion reasons can be exposed; explanations must remain faithful to the actual winning signals.

Seven recommendation surfaces
  1. Cold start: initial safe catalogue.
  2. Calibration: controlled positive/weak-safe slate.
  3. Weekly plan: meal-class options across 21 slots.
  4. Class dishes: ranked dishes inside a selected class.
  5. Daily meal plan: practical dish choices for the slot.
  6. Search: query/filter constrained discovery.
  7. General recommendations: full ranking/pairing pipeline.
09 · Recommendation decision tree

What happens to one candidate dish?

flowchart TD
      A[Candidate dish] --> B{Diet and meat rules pass?}
      B -->|No| Z[Reject: dietary conflict]
      B -->|Yes| C{Allergen and lifecycle rules pass?}
      C -->|No| Y[Reject: safety conflict]
      C -->|Yes| D{Never listed?}
      D -->|Yes| X[Reject: explicit exclusion]
      D -->|No| E{Not Today active?}
      E -->|Yes| W[Suppress for this IST day]
      E -->|No| F{Optional calorie lens pass?}
      F -->|No| V[Reject for this request]
      F -->|Yes| G[Compute BASE relevance]
      G --> H[Apply objective gain]
      H --> I[Add cohort class fit]
      I --> J[Preference ML adds zero today]
      J --> K[Apply dish affinity]
      K --> L{Enough safe candidates?}
      L -->|No| M[Return explicit constrained result; never relax safety]
      L -->|Yes| N[Rank and diversify]
      N --> O[Explain and return]
Invariant: shortage must not silently relax diet, allergy or explicit-exclusion gates. A truthful empty or constrained result is safer than an unsafe “fallback.”

11 · Food knowledge system

Useful ontology, bounded graph, uneven depth

Meal genome

Each dish carries structured attributes: cuisine/zone, diet, ingredients, time, calories, spice, texture/taste/signature and planning class.

Taxonomies

Ingredient master, cuisine master/groups, 131 meal classes, tags, state/zone normalization and synonyms.

Food graph

In-memory traversal of dish→ingredient and curated substitutions; breadth-first depth bounded 1–6 with provenance.

Knowledge provenance

Several records carry sources or verified/stub flags, but coverage and evidence rigor differ by domain.

Contextual science

Regional priors, comfort heroes, weather rules, cohort class plans and Q15 objective weights influence ranking.

Missing semantics

Recipe yield/retention, robust nutrient provenance, allergen derivatives, festival calendar and clinically governed suitability.

Terminology rule: call the present implementation a bounded food graph, not a comprehensive knowledge graph. A true product knowledge graph needs canonical entities, typed relationships, assertion-level provenance, versioning, contradiction handling and governance.

14 · Deployment and operations

Production-shaped, with three launch-critical checks open

Recommendation service

Multi-stage Docker image pinned to Python 3.11.15 slim-bookworm digest; non-root runtime; Fly app in Mumbai (bom), 512 MB shared CPU, HTTPS, one minimum machine, rolling deploy.

Supabase

Auth, public-schema Postgres, RLS, Edge Functions, scheduled retention/hard-delete and morning-notification work.

CI/CD

Backend Deno checks, Python lint/type/bundle/tests, mobile type/Jest/export, quality gate, manual persona journeys, Fly staging/production workflows and backup/mirror workflows.

Fast reference for humans and AI agents

A. Critical invariants
  1. Hard safety gates precede and cannot be overridden by scoring or ML.
  2. Never invent a missing scoring parameter; configuration absence is an error or safe no-op.
  3. Distinguish repository implementation, documented deployment and proposed future state.
  4. s_pref is inactive until a reviewed artifact and explicit activation gate exist.
  5. The current graph is bounded dish/ingredient/substitution traversal, not a universal food graph.
  6. Record catalogue/bundle and rule/model versions in decision evidence.
  7. Clinical suitability requires independent governance; nutrition data alone is insufficient.

D. AI-agent context contract

Before changing recommendation behavior, an agent should identify the relevant hard gate, configuration source, scoring phase, surface, persistence path and tests. It must say whether the change affects repository-only behavior or a deployed system. New food assertions need stable entity IDs, source, license, version, confidence, reviewer and effective dates. New ML must preserve the deterministic fallback.
